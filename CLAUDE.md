# Project: Fermentation Data Dashboard

A demo pipeline that turns raw fermentation/bioprocess data from four
different kinds of source system into a single queryable run database and
dashboard. All data is synthetic and generated by this repo.

## Data sources modeled

1. **Bioreactor control systems** — continuous, regular-interval time series
   (pH, DO, temp, agitation, gas flow, pressure). Two export patterns:
   one file per vessel (DASGIP-style — `#` header block, units in column
   names, gas flow in L/h) and multiple vessels in one wide file
   (Ambr-style — no run id anywhere in the file).

2. **Analytical instruments** — discrete, sample-triggered peak tables
   (HPLC/LC-DAD/GC-MS style): retention time, peak area/height, calculated
   concentration. Timestamped at injection, not at sample draw.

3. **Offline/manual measurements** — biomass (OD600, dry cell weight),
   hand-entered spreadsheet CSV with split date/time columns and occasional
   blank cells.

4. **Auxiliary online sensors** — off-gas analyzers (CO2/O2) and
   capacitance/dielectric probes. Continuous, but independently logged, each
   on its own unsynced clock and cadence.

## Architecture

- **Common intermediate schema**: every source normalizes to
  `run_id, timestamp, source, variable, value, unit`, plus `elapsed_h` for
  plotting and `source_file` for provenance.
- **Ingestion** (`src/ingestion/`): one pure parser per source family, a
  canonical variable/unit registry, and run identity resolution — only two of
  the six file formats state their `run_id` internally.
- **Alignment** (`src/ingestion/align.py`): cross-source joins happen at read
  time via `merge_asof` with a tolerance, so storage stays lossless and
  tolerances stay tunable without re-ingesting.
- **Storage** (`src/storage/`): SQLite with three tables (`runs`,
  `observations`, `samples`), rebuilt from scratch rather than upserted.
- **Dashboard**: Streamlit + Plotly — multi-run comparison and single-run
  drill-down. Deploys to Streamlit Community Cloud.
- Optional stretch: exportable summary report (python-pptx or PDF).

## Conventions

- Parsers take a path and return a long DataFrame. They never do cross-source
  work — anything needing two sources at once lives in `normalize.py`.
- Vendor columns map to canonical variables through explicit tables in
  `schema.py`, not pattern matching on column names.
- A variable has exactly one unit everywhere, enforced by
  `validate_observations`. Gas flow is L/min; DASGIP logs L/h and is scaled.
- Unmeasured values are dropped rows, not NaN values.
- An unrecognized `run_id` raises rather than passing through — orphan rows
  join to nothing and vanish silently from every view.

## Commands

```bash
python -m src.generators.generate_all      # write synthetic raw sources
python -m src.storage.build_db --rebuild   # normalize + load into SQLite
streamlit run streamlit_app.py             # dashboard (self-builds if data/ is empty)
pytest -q
```

`data/` is gitignored in full. Both the raw sources and the database are
regenerable from the commands above, so neither belongs in version control.

## Dashboard conventions

- Panels are declared as data in `src/dashboard/panels.py`, not built in code.
  Adding a variable is a list entry.
- **Never a dual-axis chart.** Two measures of different scale get two panels
  sharing an x-axis, never two y-scales on one plot.
- Categorical colours are assigned in fixed slot order from a validated
  palette and never cycled. A colour below 3:1 against the surface must carry
  a direct label.
- Sparse sources (analytical, offline) draw as markers, never lines — joining
  seven HPLC injections asserts values nobody measured.
- Traces over ~2000 points render via `Scattergl`. The renderer changes, the
  data never gets downsampled.
- Runs are only compared within a **cohort** (`system, strain, mode`), derived
  from the manifest rather than hardcoded. Cross-organism overlays are
  prevented by construction.
- The comparison view highlights one run against a grey cohort, using two
  colours whatever the cohort size. A colour-per-run overlay caps at three on
  this palette, and cohorts are already four.

## Build order

1. Synthetic data generators — done
2. Normalization/ingestion layer into the common schema — done
3. SQLite run database — done
4. Dashboard: single-run drill-down — done
5. Dashboard: multi-run comparison — done
6. Dashboard: trends over time — deferred, not dropped

The synthetic runs all share one start timestamp (`run_definitions._BASE_START`)
and form two cohorts, so there is no calendar axis for a trends view to plot
against. Building it now would mean staggering the generated start dates purely
to give a chart something to sit on. It waits until the run set genuinely
spans time.
